# 調査の手順: $ARGUMENTS

**調査を始める前と、レポートを出す前に必ず通す。**
理由・実例・詳細は `${CLAUDE_PLUGIN_ROOT}/skills/research/method.md`（このスキルは手順だけ）。

**2つの一線の調査版がこれ：**
- **不明な場合に仮の値を入れて処理を続けない** → 確認できないことは `要確認:` と書く。埋めない
- **完了とは動作確認済みであること** → 完了とは**一次出典を自分で開いたこと**。検索要約を読んだだけは未完了

---

## STEP 1｜決定から逆算して問いを絞る（着手前）

書き出してから調べ始める。これを書けないなら、まだ調べ始めない。

```
決定：この調査は何を決めるためのものか（1文）
選択肢：A / B / C
切り分ける問い：選択肢を分岐させる問いだけ（3〜6個）
捨てる問い：面白いが決定を変えない問い（理由つきで記録）
打ち切り基準：STEP 5 の4条件
```

## STEP 2｜情報源の階層を守って集める

**検索は「どのページを読むか決める」ためだけに使う。検索結果は出典にしない。**

| 優先 | 使うもの |
|---|---|
| 1 | 公式リファレンス・仕様書・ソースコード・**自分で取った実測値** |
| 2 | 発行元のブログ・リリースノート・公式ヘルプ |
| 3 | 第三者ブログ（**日付がなければ使わない**） |
| ✕ | 検索スニペット・AI 要約・SEO まとめ記事 |

必ずやること：

- [ ] 引用する主張の一次ページを **WebFetch で自分で取得する**
- [ ] 取得できなかったら「HTTP 403 で到達不能」等を**そのまま記録**する（無かったことにしない）
- [ ] **ベンダーは費用と上限を別ページで確認する**。ブログには書いていない
      （例: Figma MCP の書き込みは「ベータ中のみ無料・将来 usage-based 有料」。ブログには記載なし）
- [ ] 複数出典が同一の出所に帰着していないか、各記事のリンク先を辿って確認する

## STEP 3｜LLM 固有の失敗を潰す（省略不可）

レポートに書いた**固有名詞・数値・URL・API 名・オプション名を全部拾い**、
1つずつ「取得したか / 記憶から書いたか」を仕分ける。記憶から書いたものは3択のみ：

**① 検索して裏を取る ／ ② 削る ／ ③ `要確認:` を付ける**

| 失敗 | 潰し方 |
|---|---|
| URL の捏造 | **書く前に開く。開けないなら載せない** |
| API 名・オプション名の捏造 | 公式リファレンスの該当ページの該当行を見る |
| パッケージ名の捏造 | PyPI / npm で実在を確認（LLM の提案の 19.7% は実在しない） |
| 数字の伝言ゲーム | **分母を書く。割合と実数を割り算して合うか確かめる** |
| 見つからない＝存在しない | 公式一覧に無い→「未提供」。検索で出ない→「**要確認**」 |
| 自分の出力で検証 | 同じモデルに聞き直さない。**外部（実ページ・実 API・実ファイル）で確かめる** |
| 記憶と最新情報の混同 | バージョン・価格・対応状況は**必ず取得し直す** |

## STEP 4｜反証を探す

推奨案を決めたら、**推さない理由を最低3つ**探しに行く。検索語を反転させる：

```
"<対象> limitations" / "<対象> pricing" / "<対象> deprecated" / "<対象> 問題点"
```

**一般化していないか点検する**（最も多い失敗の型。詳細は method.md §5-2）：

- [ ] あるバージョン・プラン・ベータ期間で成立する事実を、他に広げていないか
- [ ] 名前の似た別概念を混同していないか
      （例: Notion の "limit" は **UI のリレーション設定（1 page / No limit）** と
      **API の1リクエスト100件上限** の2つがあり、別物）

## STEP 5｜打ち切る

**4条件を全部満たしたら打ち切る。満たさないまま終わるなら「調査完了」と書かない。**

1. 各選択肢の **費用・制限・前提条件**が一次情報で埋まっている
2. 新しく開いたページが既知の情報しか返さない状態が**3ページ続いた**
3. STEP 4 の反証検索を実施し、出てきた反証を本文に反映した
4. 残った不明点が**すべて `要確認` として明示**され、確認方法が書かれている

## STEP 6｜書く

**ラベルは4つだけ。省略は減点ではなく事故。**

| ラベル | 意味 | 必ず添える |
|---|---|---|
| （無印） | 事実。一次で確認済み | URL + 確認日 |
| `推測:` | 出典に書かれていない推論 | 根拠 + 確度語 + 外れた場合の影響 |
| `提案:` | 意見・推奨 | 前提と、前提が崩れたらどうなるか |
| `要確認:` | 確認できなかった | **どうすれば確認できるか**を1行 |

確度語は4つだけ：**ほぼ確実（90%+）／可能性が高い（60-90%）／五分五分（40-60%）／可能性は低い（10-40%）**。
「五分五分」は決定を保留すべき合図。混ぜて使わない。

出典の書式：

```
主張（本文）。
— <URL>（確認日 YYYY-MM-DD／ページ表記 "Last updated ..." があれば併記）
```

**冒頭へ必ず置く**（読み手は有料インフラを避けたく、実務で使える結論を求めている）：

```markdown
## 結論（3行）
1. 推奨：<何を、いつ、誰が>
2. 費用：<無料 / 月額◯円 / ベータ中のみ無料・将来従量課金>
3. 次の一手：<今日できる具体的な操作を1つ>
```

**比較表に費用の列が無ければ不合格。** 末尾に必ず「要確認」表を置く（空欄にしない）。

## STEP 7｜出す前の点検

```
□ 決定を1文で書けるか
□ 主要な主張すべてに一次/準一次の出典があるか
□ URL を全部自分で開いたか／全部に確認日があるか
□ 数値に分母があり、割り算が合うか
□ ベンダーの費用・上限を別ページで確認したか
□ 循環報告（複数出典が同一の出所）を確認したか
□ 反証検索をやったか
□ 4ラベルと確度語が統一されているか
□ 「要確認」表があり、確認方法まで書いてあるか
□ 冒頭に結論3行、比較表に費用の列があるか
□ 記憶から書いた固有名詞・数値が残っていないか
□ 「見つからなかった」を「存在しない」と書いていないか
```

**出典一覧には「取得」列を付ける：◎＝本文を読んだ／△＝検索要約のみ（＝要確認扱い）。**
△ が残っていても出してよいが、**△ であることを隠さない。**

## 絶対にやらないこと

| 行為 | 理由 |
|---|---|
| 確認できない数値・URL・価格をそれらしい値で埋める | 一線その1。`要確認:` で残す |
| 検索スニペットを出典として引用する | 三次情報。要約器が一段挟まった時点で数字の意味が変わる |
| 開いていない URL を載せる | 捏造。開けなかったなら 403/404 と書く |
| 「複数の記事が言っている」を裏付けにする | 循環報告の可能性。出典を辿って独立性を確認する |
| 推測を無印で書く | 読み手の判断を誤らせる。ラベルを付ける |
| 調査中に外部サービスへ書き込む | 調査は読み取りのみ（Notion / Figma / Sheets / Slack 等） |
| 他エージェントが編集中のファイルを触る | 着手前に確認する |

## 既存レポートを磨き直す場合

1. レポート中の**全ての数値・URL・固有名詞**を列挙する
2. 各項目を STEP 2 の階層で分類（一次／準一次／二次／三次）
3. **二次・三次しか出典が無い主張について、一次を探しに行く**
4. STEP 3 の表で機械的に潰す（特に分母と URL の実在）
5. **ベンダー案件は費用の再確認**を最優先（ベータ・従量課金の見落としが起きやすい）
6. STEP 6 のラベル・確度語・出典書式に書き直し、「要確認」表と「取得」列を追加する
