# 調査方法論 — 調査そのものの質を上げる

作成日: 2026-08-12
対象: hicard で調査タスクを行う人・エージェント全員
実践手順（短縮版）: `.claude/skills/research/SKILL.md`

このドキュメントは「何を調べるか」ではなく「**どう調べれば信じてよい結論になるか**」を扱う。
スプレッドシート・Figma×AI・Notion の各調査は、この基準に照らして磨き直す。

## 0. 知識の置き場所

| 層 | 置き場所 | 内容 |
|---|---|---|
| 1. 一線 | 下の2原則 | 「不明な場合に仮の値を入れて処理を続ける」禁止／「完了＝一次出典を自分で開いたこと」 |
| 2. 手順 | `skills/research/SKILL.md` | 調査を始めるとき必ず踏む STEP |
| 3. 理由と実例 | **このファイル** | なぜその手順なのか、失敗の実例、判断基準 |
| 4. 個別の事実 | 作業リポジトリの `docs/research/*.md` 等 | 各テーマの調査結果そのもの |

3 と 4 を混ぜない。**このファイルには「どの調査にも効く話」だけを書く。**
特定サービスの仕様は調査結果の側に書く（§5-2 の「一般化の誤り」を避けるため）。

## 1. 情報源の評価

### 原則 1-1｜主張の重さに応じて、一次情報まで降りる

**なぜ**：二次情報は要約の過程で必ず情報を落とす。落ちるのは往々にして
「分母」「前提条件」「例外」「費用」——つまり意思決定に一番効く部分。

**一次／二次の区別（このリポジトリでの定義）**

| 階層 | 何が該当するか | 例 |
|---|---|---|
| 一次 | 発行元自身が出した仕様・公式ドキュメント・ソースコード・**自分で取った実測値** | `developers.figma.com` のツール一覧、`arxiv.org` の論文本文、`preflight()` の出力 |
| 準一次 | 発行元のブログ・リリースノート・公式ヘルプ | `figma.com/blog/...`、`notion.com/help/...` |
| 二次 | 第三者の解説・技術ブログ・ニュース | Medium 記事、まとめブログ |
| 三次 | Wikipedia、SEO まとめ、AI 生成要約、**検索結果のスニペット** | 「〜10選」記事 |

**具体例（今回の調査で実際に起きた）**

LLM が存在しない npm/PyPI パッケージを提案する率について、二次情報は
「**19.7%**」という数字を繰り返している。ところが一次（論文本文）を読むと：

> "These 30 tests generated a total of 2.23 million packages in response to our prompts,
> of which 440,445 (19.7%) were determined to be hallucinations."
> — Spracklen et al., USENIX Security 2025 / arXiv:2406.10279（確認日 2026-08-12）

分母は **2.23 百万個の「パッケージ参照」**であって、生成した 576,000 件のコードサンプルではない。
実際、コードサンプル単位で見ると「少なくとも1個の架空パッケージを含むサンプル」の割合になり、
まったく別の数字になる。**二次情報を引くと「19.7%」だけが残り、分母が消える。**

さらに悪いことに、私がこの論文本文を最初に取得したとき、要約器は
「576,000 code samples ... 440,445 (19.7%)」と返してきた。440,445 / 576,000 = 76% で
算数が合わない。**引用する数字は必ず割り算して整合を確かめる。**

**チェック**
- [ ] 数値を1つでも載せるなら、その数値の**分母**を書けるか
- [ ] 割合と実数の両方を書いたとき、割り算が合うか
- [ ] 二次情報しか出典がない主張が残っていないか。残るなら「二次情報のみ」と明記したか

### 原則 1-2｜情報の鮮度は「記事の日付」ではなく「対象の変更速度」で測る

**なぜ**：ソフトウェアの仕様は数か月で変わる。日付のない記事は、
「古い」のではなく「**いつの話か判定不能**」であり、それは古い記事より危険。

**具体例**：Google Sheets API のクォータを一次で確認した（確認日 2026-08-12）。

> Read requests — Per minute per project: 300 / Per minute per user per project: 60
> Write requests — Per minute per project: 300 / Per minute per user per project: 60
> — https://developers.google.com/workspace/sheets/api/limits （ページ表記 "Last updated 2026-07-31 UTC"）

「Google Sheets の読み取りクォータは 60回/分」は正しい。
ただし正確には「**プロジェクトあたりのユーザ単位で** 60/分」で、プロジェクト全体では 300/分。
GitHub Actions のようにサービスアカウント1つで回す場合は 60 の側に当たる。

**運用ルール**
- 出典 URL には**必ず確認日を付ける**。ページ側に "Last updated" があればそれも書く
- 学術論文・仕様書のように内容が固定される文書は確認日不要でもよいが、
  **変わりうるページ（ヘルプ・ドキュメント・価格表）には確認日を必ず付ける**
  （APA 7 の retrieval date の考え方と同じ：変化する非アーカイブページにのみ取得日を付す）
- 日付が書かれていない記事は、**それだけで二次情報から三次情報に格下げする**

### 原則 1-3｜「複数の記事が同じことを言っている」は裏付けにならない

**なぜ**：同一の出所から派生した記事が連鎖しているだけの場合がある。
これは source criticism で **circular reporting（循環報告）／citogenesis** と呼ばれる。
Wikipedia の記述が報道に引用され、その報道が Wikipedia の出典として貼られて閉ループになる現象。
（Randall Munroe が xkcd で命名。出典: https://en.wikipedia.org/wiki/Circular_reporting 確認日 2026-08-12。
なお Wikipedia は三次情報であり、命名の初出そのものは未確認＝**要確認**）

**見抜き方（実行可能な手順）**
1. 各記事の**出典欄・リンク先**を辿る。3本のうち3本が同じ1本を指していれば、独立な確認は1件
2. **同一の言い回し・同一の数字の丸め方**が複数記事に現れたら、コピー元がある
3. 記事の**公開日順に並べる**。最古の記事が一次を引いていなければ、その系統全体が根拠不明
4. 数字が伝言ゲームで変わっていないか（原則 1-1 の分母消失が典型）

**具体例（今回の調査で遭遇）**：AI による架空判例引用の制裁事例データベースの件数について、
二次媒体の記述が食い違っていた——「1,598 件（2026-06-09 時点）」「約 1,490 件（2026-05 時点）」
「1,313 件」。一次（Damien Charlotin のデータベース本体）は HTTP 403 で取得できなかった。
よって**本ドキュメントではこの件数を数値として採用しない**。
→ **要確認**：https://www.damiencharlotin.com/hallucinations/ に直接アクセスできる環境で件数と基準日を確認する。

### 原則 1-4｜ベンダー資料は「できること」の一次情報だが、「できないこと」「費用」の一次情報ではない

**なぜ**：発行元は自社に有利な情報を選択的に出す。医学分野では、
企業がスポンサーの研究はスポンサー製品に有利な結論が出やすいことが定量化されている
（Lundh et al., Cochrane Database of Systematic Reviews 2017: 有利な結論の RR 1.34, 95%CI 1.19–1.51。
出典: https://www.cochranelibrary.com/cdsr/doi/10.1002/14651858.MR000033.pub3/full 確認日 2026-08-12。
**注：検索要約経由。本文は未読＝要確認**）。ソフトウェアのベンダー資料も構造は同じ。

**対処**：ベンダー資料を読むときは、宣伝ページではなく以下を見る。

| 知りたいこと | 見る場所 |
|---|---|
| 何ができるか | ブログ・製品ページ（ここは信頼してよい） |
| **制限・上限** | API リファレンスの limits / quotas ページ |
| **費用** | pricing ページ + ドキュメント中の「beta」「usage-based」の記述 |
| **できないこと** | ツール一覧に**無い**もの、changelog、issue tracker |

**具体例（hicard に直接効く）**：調査結果のファイル（例 `docs/research/figma_ai.md`）は
「Claude Code × Figma MCP の Code to Canvas」を第1候補として
「**追加コストゼロ**」と書き、出典は muz.li と Medium の記事（＝二次情報）だけを挙げている。

一次にあたると（すべて確認日 2026-08-12）：

- 公式発表は実在し、日付も合う（2026-02-17）
  https://www.figma.com/blog/introducing-claude-code-to-figma/
- キャンバスに**書き込む**ツールは `use_figma` / `generate_figma_design` / `upload_assets` の3つ
  https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/
- そして開発者ドキュメントにはこう書かれている——
  **"currently available for free during the beta period"、将来は "usage-based paid"**

つまり「追加コストゼロ」は**現時点では正しいが、恒久的な事実ではない**。
有料インフラを避けたい判断者にとって、この一文の有無は意思決定を変える。
二次情報だけを見ていると、この一文は最後まで出てこない。

**チェック**
- [ ] 採用候補それぞれについて「費用」列を書けるか（無料／有料／**ベータ中のみ無料**）
- [ ] 「無料」と書くとき、それが恒久なのか期間限定なのか一次で確認したか

### 原則 1-5｜プロの検証者のやり方を真似る（SIFT / lateral reading）

Mike Caulfield の SIFT（Stop / Investigate the source / Find better coverage /
Trace claims back to the original context）。出典: https://hapgood.us/2019/06/19/sift-the-four-moves/
（2019-06-19、確認日 2026-08-12）

要点は **lateral reading**：怪しいページの中を読み込むのではなく、**そのページから離れて**
第三者がその出所をどう評価しているかを見る。ページ内の作り込み（デザイン・引用の多さ）は
信頼性の指標にならない。

hicard 版に翻訳すると：
- **S**：読み始める前に「この出所は誰か」を確認する
- **I**：ブログなら著者、企業なら立場（売り手か、利用者か、競合か）
- **F**：同じ主張について**より良い出所**を探す（記事より公式ドキュメント、公式ドキュメントより実測）
- **T**：数字・引用・図は**初出まで辿る**（原則 1-1）

## 2. LLM が調査するときに固有の失敗

LLM の失敗は「たまに間違える」ではなく**構造的で、再現する**。
Kalai ら（OpenAI）は、モデルが幻覚を出すのは学習と評価が
「不確実性を認めるより当てずっぽうを報酬する」ためだと論じている
（"Why Language Models Hallucinate", arXiv:2509.04664, 2025-09-04。確認日 2026-08-12。
https://arxiv.org/abs/2509.04664 ）。
**つまり「知らない」と言わない傾向は、モデルの癖ではなく最適化の帰結**であり、
運用側が手順で潰すしかない。

### 失敗 2-1｜学習データの知識と検索で得た情報を混ぜる

**症状**：検索していない事柄を、検索で確認したかのような口調で書く。
特に「バージョン」「価格」「対応状況」で起きる。

**なぜ危険か**：学習データの実効カットオフは公称カットオフと一致しない。
古いクロールが新しいダンプに混入するため、トピックごとにカットオフがずれる
（Cheng et al., "Dated Data: Tracing Knowledge Cutoffs in Large Language Models",
arXiv:2403.12958。確認日 2026-08-12。**検索要約のみ・本文未読＝要確認**）。
自分の「知っている」がいつ時点なのかは、自分では分からない。

**防ぎ方（省略不可）**
- レポート内の**全ての固有名詞・数値・URL・オプション名**について、
  「検索/取得したか」「記憶から書いたか」を自分で仕分けする
- 記憶から書いたものは、**削るか、検索で裏を取るか、`要確認` を付けるか**の3択。第4の道はない

### 失敗 2-2｜もっともらしい URL・API 名・オプション名を捏造する

**定量的な裏付け**：コード生成 LLM が提案するパッケージのうち **19.7%（440,445 / 2.23M）**が
実在しないパッケージだった。しかも架空名は**再現する**——同一プロンプトを10回反復した際、
架空パッケージの **43% が10回すべてで再出現**、**58% が2回以上再出現**した。
（Spracklen et al., USENIX Security 2025 / arXiv:2406.10279。確認日 2026-08-12。
https://arxiv.org/html/2406.10279v3 ）

**「再現するから正しい」は成り立たない。** 同じモデルに聞き直す検証は無意味。

**防ぎ方**
- URL は**書く前に開く**。開けないなら載せない
- API 名・関数名・オプション名は**公式リファレンスの該当ページで該当行を見る**。
  「たぶんこういう名前」で書かない
- ライブラリ・パッケージ名は**レジストリ（PyPI / npm）で実在を確認**してから書く
- 引用は**コピー＆ペースト**する。記憶で言い換えない

**今回このルールで実際に落ちたもの**：`intelligence.gov` / `dni.gov` / `archive.dni.gov` の
ICD 203 PDF はすべて HTTP 403 だった。URL を「載せられるはずのもの」として書かず、
実際に取得できたミラー（`bmbs.org`）を出典として明記した。§7 参照。

### 失敗 2-3｜検索結果の要約だけ読んで一次にあたらない

**症状**：検索スニペットの内容を、あたかも原文を読んだかのように引用する。

これは実害が出る。今回、同じ論文本文に対して**取得の仕方を変えただけで
返ってきた数字の意味が変わった**（原則 1-1 の 576,000 vs 2.23M）。
検索スニペットは**三次情報**であり、要約器が一段挟まった時点でさらに劣化する。

**防ぎ方**
- 検索は「どのページを読むか決める」ためだけに使う。**検索結果は出典にしない**
- 引用する主張の一次ページは**必ず自分で取得する**
- 取得できなかったものは、レポートに「検索要約のみ・本文未読」と書く
  （本ドキュメントの §7 でも実際にそう分類している）

### 失敗 2-4｜「見つからなかった」を「存在しない」と結論づける

**なぜ危険か**：これは argument from ignorance（無知に訴える論証）。
ただし**常に誤りとは限らない**——適切な条件下で十分に探して見つからなければ、
それ自体が（弱い）証拠になる。分かれ目は「探し方が適切だったか」。

**書き分けの規則**

| 状況 | 書き方 |
|---|---|
| 公式ドキュメントの網羅的な一覧に載っていない | 「公式ツール一覧（URL, 確認日）に記載なし。**未提供と判断**」 |
| 検索したが出てこなかった | 「検索語 X / Y で発見できず。**存在しないとは断定しない（要確認）**」 |
| アクセスできなかった | 「一次に到達できず（HTTP 403 等）。**要確認**」 |

**具体例**：Figma MCP のキャンバス書き込みは、公式ツール一覧に `use_figma` 等が
**載っている**ことで確認できた。逆に「Figma MCP には X という機能がない」と書きたいときは、
同じ一覧に無いことを根拠に**一覧の URL と確認日を添えて**書く。検索で出なかったことは根拠にしない。

### 失敗 2-5｜自分の出力を検証に使う

同じモデルに「これは正しい?」と聞き直しても、失敗 2-2 の再現性により同じ嘘が返る。
**検証は必ず外部（実際のページ・実際の API・実際のファイル）に対して行う。**

## 3. 調査設計

### 原則 3-1｜「何を知れば意思決定できるか」から逆算して問いを立てる

**なぜ**：網羅的な情報は意思決定を助けない。決定を分岐させる情報だけが助ける。
Heuer の ACH（Analysis of Competing Hypotheses）の中心概念 **diagnosticity（診断力）**は、
「その証拠が仮説間をどれだけ切り分けるか」であり、証拠の量や入手しやすさではない。
（Heuer, *Psychology of Intelligence Analysis*, 1999。レビュー: Dhami et al., *Applied Cognitive
Psychology*, 2019, https://onlinelibrary.wiley.com/doi/full/10.1002/acp.3550 確認日 2026-08-12。
**検索要約のみ・本文未読＝要確認**）

**手順**
1. **決定を書く**：「Figma 連携で最初に何を実装するか」
2. **選択肢を書く**：A. 公式 MCP の書き込み / B. OSS の書き込み MCP / C. 読み取りのみ
3. **選択肢を切り分ける問いだけを書く**：費用は？ NDA ファイルで使えるか？ 既存 DB と繋がるか？
4. **切り分けない問いを消す**：「Figma AI の歴史」「他社の導入事例10選」は決定を変えない

### 原則 3-2｜先に反証を探す（ACH と pre-mortem）

**なぜ**：確証バイアスにより、人も LLM も仮説を支持する情報を先に見つけてしまう。
ACH は「支持証拠が最も多い仮説」ではなく「**矛盾する証拠が最も少ない仮説**」を選ばせることで
これを構造的に潰す。

**併用する道具：pre-mortem**（Klein, *Harvard Business Review*, 2007）。
「このプロジェクトは1年後に失敗した。なぜか?」と**失敗を既成事実として**逆算させる方法。
prospective hindsight により、通常のリスク洗い出しに比べ挙がるリスクが増えることが知られる。
（出典: https://hbr.org/2007/09/performing-a-project-premortem ／PDF 版
http://homepages.se.edu/cvonbergen/files/2013/01/Performing-a-Project-Premortem.pdf 確認日 2026-08-12。
**検索要約のみ・本文未読＝要確認**）

**調査に落とすと**
- 推奨案を決めたら、**その案を推さない理由を最低3つ探しに行く**（検索語を反転させる：
  "X limitations" / "X pricing" / "X deprecated" / "X 問題点"）
- レポートに「この結論が間違っているとしたら、原因はこれ」を1節書く

### 原則 3-3｜打ち切りの基準を先に決める

**なぜ**：「どこまで調べたら十分か」を決めずに始めると、無限に調べるか、
最初の1本で止まるかのどちらかになる。質的研究では **saturation（飽和）**——
新しいデータが新しい知見を生まなくなった点——が停止基準として使われ、
近年は量より**information power（情報の力：サンプルが目的に対して持つ情報量）**で
判断すべきとされる。（確認日 2026-08-12。**検索要約のみ・本文未読＝要確認**）

**hicard 版の打ち切り基準（決定に紐づける）**

以下を**全部**満たしたら打ち切る：

1. 各選択肢について、**費用・制限・前提条件**が一次情報で埋まっている
2. 新しく開いたページが**既知の情報しか返さない**状態が3ページ続いた
3. 反証検索（原則 3-2）を実施し、出てきた反証を本文に反映した
4. 残った不明点が**すべて「要確認」として明示**され、確認方法が書かれている

満たさないまま時間切れになった場合は、**そう書く**。「調査完了」と書かない。

### 原則 3-4｜決定に効かない調査は切る

途中で「これは面白いが決定を変えない」と気づいたら、その場で止めて
レポートの「調べなかったこと」欄に理由付きで書く。**書かずに黙って切らない**
（読み手が「調べ漏れ」と「意図的な除外」を区別できなくなる）。

## 4. 成果物の書き方

### 原則 4-1｜事実・推測・意見をラベルで分ける

**なぜ**：米国情報コミュニティの分析基準 ICD 203 は、9つの tradecraft standards の第3項で
これを明示的に要求している（署名 2015-01-02。技術修正あり）：

> **(3) Properly distinguishes between underlying intelligence information and analysts'
> assumptions and judgments**: Analytic products should clearly distinguish statements that
> convey underlying intelligence information used in analysis from statements that convey
> assumptions or judgments. Assumptions are defined as suppositions used to frame or support
> an argument... Judgments are defined as conclusions based on underlying intelligence
> information, analysis, and assumptions. Products should state assumptions explicitly when
> they serve as the linchpin of an argument or when they bridge key information gaps.
> Products should explain the implications for judgments if assumptions prove to be incorrect.

（出典: ICD 203 *Analytic Standards*。取得先は §7 参照。確認日 2026-08-12）

**hicard で使う4ラベル（この4つだけ。増やさない）**

| ラベル | 意味 | 必須で添えるもの |
|---|---|---|
| （無印） | **事実**。一次情報で確認済み | URL と確認日 |
| `推測:` | 事実からの推論。出典に書かれていない | 根拠 + 確度語（下記）+ 外れた場合の影響 |
| `提案:` | 意見・推奨。hicard の事情を加味した判断 | 前提と、前提が崩れた場合にどうなるか |
| `要確認:` | 確認できなかった。到達不能・時間切れ・情報なし | **どうすれば確認できるか**を1行 |

**読み手が最も困るのは「推測を事実として書かれること」。ラベルを省くのは減点ではなく事故。**

### 原則 4-2｜確度は決まった語彙で書く

ICD 203 は確度表現を7段階に固定し、混用を禁じている（原文の表、確認日 2026-08-12）：

| almost no chance | very unlikely | unlikely | roughly even chance | likely | very likely | almost certain(ly) |
|---|---|---|---|---|---|---|
| 01–05% | 05–20% | 20–45% | 45–55% | 55–80% | 80–95% | 95–99% |

また ICD 203 は「likelihood（事象の起こりやすさ）」と「confidence（判断の根拠の強さ）」を
**同じ文に混ぜてはならない**と定めている。

`提案:` — 7段階は実務には細かすぎる。hicard では**以下の4語に縮約**して使う
（この縮約は本ドキュメントの判断であり、ICD 203 の記述ではない）：

| 語 | 目安 | 使う場面 |
|---|---|---|
| ほぼ確実 | 90%以上 | 一次情報が明示、または実測済み |
| 可能性が高い | 60–90% | 一次情報から論理的に導ける |
| 五分五分 | 40–60% | 根拠が拮抗。**決定を保留すべき合図** |
| 可能性は低い | 10–40% | 反証が優勢だが排除しきれない |

「根拠の強さ」は別に書く：`根拠: 一次1本のみ` / `根拠: 一次2本＋実測`。

### 原則 4-3｜出典の付け方

```
主張（本文）。
— <URL>（確認日 2026-08-12／ページ表記 "Last updated 2026-07-31"）
```

- **URL は自分が実際に開いたものだけ**を書く（失敗 2-2）
- 一次に到達できずミラー等で代替した場合は、**代替した事実も書く**
- 引用は原文をコピーする。訳す場合は原文を併記する
- 論文は arXiv 番号など**恒久識別子**を書く（URL は変わる）

### 原則 4-4｜「わからなかったこと」を専用の節にまとめる

レポート末尾に必ず置く。形式：

```markdown
## 要確認（この調査で確認できなかったこと）

| # | 確認できなかったこと | 理由 | 確認方法 |
|---|---|---|---|
| 1 | 判例DBの正確な件数 | 一次サイトが HTTP 403 | ブラウザで直接アクセスして基準日つきで記録 |
```

**空欄にしない。**「特になし」と書くのは、原則 3-3 の打ち切り基準を全部満たした場合だけ。

### 原則 4-5｜判断者向け要約の作り方

hicard で調査を受け取る側に共通する読み方の前提：
**有料インフラを避けたい／実務で使える結論を求める／推測を事実として書かれることを嫌う。**

冒頭に必ずこの3点セットを置く：

```markdown
## 結論（3行）

1. 推奨：<何を、いつ、誰が>
2. 費用：<無料 / 月額◯円 / ベータ中のみ無料・将来従量課金>
3. 次の一手：<今日できる具体的な操作を1つ>
```

その下に**比較表**（選択肢 × 費用 / 制限 / 前提 / 着手コスト）。
本文の詳細はその後。**費用の列を落とした比較表は不合格。**

## 5. 2つの一線と、その適用

### 5-1｜2つの一線（調査版）

> **絶対にやらないこと：不明な場合に仮の値を入れて処理を続ける**

調査版：**確認できなかった数値・URL・API 名・価格を、それらしい値で埋めない。**
`要確認:` として残す。埋めるくらいなら、その行を丸ごと削る。

> **原則：「完了」とは動作確認済みであること**

調査版：**「完了」とは、載せた主張の一次出典を自分で開いたこと。**
検索して要約を読んだだけは完了ではない。

**実装の完了条件を、調査の完了条件へ読み替える**

| # | 実装版 | 調査版 |
|---|---|---|
| 1 | スクリプトを実際に実行した | **一次ページを実際に取得した**（403/404 も記録） |
| 2 | ログを読んだ | 取得した本文の**該当箇所を読んだ**（要約器の出力ではなく） |
| 3 | ファイルパスが実在する | **URL が実在して開ける**。数値の分母が合う |
| 4 | 外部API・認証が通っている | 反証検索を実施した／`要確認` 欄が埋まっている |

### 5-2｜最も多い失敗は「条件つきの事実の一般化」

過去に実際に起きた型：**あるスプレッドシートに固有の制約を、性質の違う別のシートに当てはめた。**
制約の出所を確かめずに一般化したため、**実際には被参照 0 件で安全だったものを「危険」と説明した。**

**調査における同型の誤りは「バージョン・プラン・条件の一般化」。**

| 原型の教訓 | 調査版 |
|---|---|
| 対象固有の制約を他の対象に一般化しない | **あるバージョン／プラン／ベータ期間で成立する事実を、他に一般化しない** |
| 対象自身の依存を実際に数える | **対象そのものの公式リファレンスを、その対象について読む** |
| 「安全」と出たらためらわない | **一次で確認できたら、過剰にぼかさず言い切る**（推測ラベル不要） |

**実例1（Figma）**：「Figma MCP でキャンバスに書き込める」は事実。
しかし「だから無料」は誤った一般化——`use_figma` は**ベータ期間中のみ無料**で、
将来は usage-based の有料機能になると開発者ドキュメントに書かれている（原則 1-4）。

**実例2（Notion）**：「Organizations→Projects の relation が limit:1」という所見について、
**Notion には名前の似た "limit" が2つある**（両方とも確認日 2026-08-12）：

| どの limit か | 実体 | 出典 |
|---|---|---|
| **UI のリレーション設定** | 1つのリレーションに紐づけられるページ数を `1 page` か `No limit` で選べる。**所見はこれ** | https://www.notion.com/help/relations-and-rollups |
| **API のリクエスト上限** | 1リクエストで set/add できる関連ページは 100 件。ただし「リレーション自体は 100 件を超えて保持できる。この上限は1リクエストでの追加数のみを制限する」と明記 | https://developers.notion.com/reference/request-limits |

この2つを混同すると「Notion のリレーションは100件までしか持てない」という
**誤った制約を設計に持ち込む**。5-2 冒頭の失敗とまったく同じ構図。

**実測に相当する行為（調査版 preflight）**
- API の挙動を1回だけ読み取りで叩いて確かめる（書き込みはしない）
- 公式リファレンスの**該当ページ**を開く（トップページや検索結果ではなく）
- ツール／エンドポイントの**一覧**を取得し、対象が載っているか／載っていないかを見る

### 5-3｜守るべき境界（調査タスク中の禁止事項）

- 外部サービス（Notion / Figma / Google Sheets / Slack 等）へ**書き込まない**。調査は読み取りのみ
- 再取得できない生データを変更しない。認証情報は読み取りすらしない
- 他のエージェントが編集中のファイルに触れない（着手前に確認する）
- git commit / push は指示があったときだけ
