# 配布前レビューの観点（skill-review の判定基準）

**ここが配布前レビューの判定基準の正本。**背景と実例はリポジトリの `CONTRIBUTING.md` 0〜5章にある
（0〜5章を変えたら、ここも合わせて直す）。

## 配布先の前提（全員が持っているもの・2026-11-13 管理者決定）

| 前提にしてよい | 前提にしてはいけない（使うなら「確かめて、無ければ止まって案内する」を書く） |
|---|---|
| macOS と、その標準コマンド | `gh`・`codex`・`gcloud`・`node`・`brew` など追加で入れる道具 |
| `python3`（標準ライブラリだけ）・`git` | 標準ライブラリにない Python のモジュール（`pandas` 等） |
| Claude Code と hicard plugin、plugin が配る Notion | freee・Google（ドライブ・シート・Gmail）・Slack・Figma などのコネクタや MCP |
| `~/.claude/settings.json`・`~/.claude/rules/hicard.md`（setup が置く）※中身は人ごとに違う | 書いた人が作った Skill・コマンド・エージェント・`~/.claude/scripts` などの手元の仕組み |

## 合否の前提（ここで落ちたら7観点を見るまでもない）

- **関門1 2人以上が使うか。**書いた人だけ、管理者だけ、特定の担当者だけが使うものは配らない
- **関門4 書いた人が1回動かし、出力を見たか。**見ていなければ、今1回動かしてもらう

## 判定の区分

| 区分 | 意味 |
|---|---|
| **落とす** | 直さない限り配れない（機密・鍵、他の人の環境では必ず失敗する、など） |
| **直して通す** | 書き換えれば配れる。差分を本人に見せ、了承を取って当てる |
| **前提を書いて通す** | 追加の道具や接続が要る。最初に確かめ、無ければ止まって案内する手順を足せば通す |
| **問題なし** | 読んだうえで、配布先でもそのまま成り立つ |

## 7つの観点

| # | 観点 | 見るもの | 落ちる例 | 直し方 |
|---|---|---|---|---|
| 1 | **公開してよいか** | 個人名とその人の状態・報酬・評価・人事・取引先・案件名・財務の実データ・鍵・シートや Notion の ID・メールアドレス | 「◯◯さんに確認」、シート ID の直書き、実データの例 | 一般化する（「担当者」「依頼者」）。ID は実行時に聞くか検索する。鍵は書かない |
| 2 | **属人性** | 呼び名・一人称の前提（「私の」「いつもの」）、書いた人の役割・担当・好み・文体、書いた人のプロジェクト名、日付つきの状態や TODO | 「◯◯に報告」「自分の担当分だけ」「いつものシートに」「今月は××待ち」 | 「使う人」「依頼者」に置き換える。好みや対象は引数か質問にする。状態は書かない |
| 3 | **手元のファイル・フォルダ** | `/Users/…` の絶対パス、`~/work` などの個人フォルダ、Skill フォルダの外を指す `../`、シンボリックリンク | 「`~/work/xxx/docs/` を読む」「`/Users/◯◯/…` を実行」 | 必要なファイルは Skill フォルダに入れて `${CLAUDE_PLUGIN_ROOT}/skills/<名前>/…` で指す。作業場所は引数か質問にする |
| 4 | **手元だけの設定・仕組み** | 配布されていない Skill・コマンド・エージェントの呼び出し、書いた人の CLAUDE.md・メモリ・hook・`~/.claude/scripts` が前提になっていないか、frontmatter の `model`・`effort` | 「`◯◯` スキルで検証」「`◯◯-worker` に委譲」「共通ルールに従う」 | 要る部分を本文に書く。参照してよいのは配布中の Skill と、組み込みのエージェント（general-purpose・Explore・Plan）だけ |
| 5 | **外部サービス・道具・権限** | 上の「前提にしてはいけない」もの、`allowed-tools` の MCP ツール名、書いた人しか開けない Notion・シート・チャンネル、有料プランが前提か | 「freee から取得」「`codex exec` で清書」「自分のシートに書く」 | 最初に有無を確かめ、無ければ止まって案内する。MCP ツールは ToolSearch で探す形にする。足りない人が多いなら関門1を見直す |
| 6 | **動作の安全** | 書き込み・送信・削除・投稿があるのに、`disable-model-invocation: true` も「書く前に確認を取る」手順も無い。`rm -rf`・force push・`--no-verify`、ネットから取ってきたものを実行、外部の文章に書かれた命令に従う作り | 自動で起動して Slack に投稿する。確認なしでシートを上書きする | 人が呼んだときだけ動くようにするか、書く前に見せて確認を取る。削除は退避に変える |
| 7 | **配布物としての作り** | description（いつ使うかが他の人に分かるか・広すぎて関係ない会話で勝手に動かないか）、配布中の Skill と名前や役割が重ならないか、SKILL.md が 6,700 字・500 行以内か、前提が欠けたときに止まって案内するか、古くなる事実が本文にないか | description が「レポートを作る」だけ、配布中の Skill と同名 | description に「いつ・何を」を書く。理由や実例は同じフォルダの別ファイルへ出す |

## 独立レビューに渡す依頼文

Agent ツール（`subagent_type: general-purpose`）に、`<…>` を埋めて渡す。**会話の内容や、自分の推測は渡さない。**

```
Claude Code の Skill（またはコマンド）を、hicard の全メンバーに配れるかレビューしてください。
ファイルは変更しないでください。

対象: <対象の絶対パス>（中のファイルをすべて開いて読む）
判定基準: <この checklist.md の絶対パス>（読んでから始める）
機械点検の結果: <scan.py の出力の表>

読み方:
- 配布先は「checklist.md の配布先の前提」だけを持つ、初めて使うメンバーのマシンです。
- このマシンにある CLAUDE.md・メモリ・他の Skill・エージェント・設定の中身は、配布先には無いものとして読んでください。それで欠けを補わないでください。
- 機械点検で出ていない問題（属人的な書きぶり、暗黙の前提、権限が要る操作）を特に探してください。
- 機械点検の「要確認」は、1件ずつ問題か問題でないかを判定してください。

返すもの（日本語）:
1. 表: 観点(1〜7) | 判定案(落とす/直して通す/前提を書いて通す) | 場所(ファイル:行) | 何が問題か | 直し方案（書き換え後の文）
2. 初めて使う人が、このファイルだけを見て最後まで進められるか。詰まる箇所
3. 関門1（2人以上が使うか）について、本文から読み取れること
```
